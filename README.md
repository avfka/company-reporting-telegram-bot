# Telegram-бот для отчётности по PostgreSQL

Безопасный MVP корпоративного Telegram-бота: пользователь выбирает заранее утверждённый отчёт, бот выполняет параметризованный `SELECT` в read-only транзакции и возвращает компактную таблицу.

## Что уже есть

- минимальный ASGI webhook API без тяжёлого веб-фреймворка;
- доступ только для Telegram ID из белого списка;
- выдача отчётов только в личных чатах, без групп;
- `/whoami`, `/reports`, `/run <report> [name=value]`;
- `/reports_sks` с календарём выбора периода и отправкой инфографики и подробного `.xlsx` в Telegram;
- `/reports_dota` с календарём, динамикой запусков/выпусков и детализацией проектов;
- `/report_agents` со списком партнёров, оплаченных проектов и агентских выплат;
- `/report_agent` с выбором конкретного агента и периода создания проектов;
- `/companies` с защищённой Excel-выгрузкой компаний за выбранный период;
- SQL только из версионируемого `reports.json`;
- PostgreSQL read-only транзакция, таймаут подключения и запроса;
- лимит строк и разбиение длинных Telegram-сообщений;
- health endpoint `/health` без раскрытия секретов;
- конфигурация для Vercel и Docker;
- тесты ключевых ограничений безопасности;
- CI с тестами и аудитом production-зависимостей.

## Почему нет произвольного SQL из чата

Текстовые SQL-запросы от пользователей дают слишком большой риск утечки или изменения данных. В этом проекте запросы добавляет разработчик в `reports.json`, а значения пользователей передаются только как bind-параметры. Дополнительно запрос исполняется в read-only транзакции. Для подключения к продакшен-БД всё равно нужен отдельный пользователь только с `SELECT`.

## Быстрый запуск

1. Создайте бота через `@BotFather` и получите токен.
2. Скопируйте `.env.example` в `.env` и заполните значения.
3. Создайте read-only пользователя PostgreSQL по примеру `docs/postgres_readonly_role.sql`.
4. Установите зависимости и запустите API:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
set -a; source .env; set +a
uvicorn app:app --reload
```

5. Для локального webhook используйте HTTPS-туннель. Задайте публичный URL и зарегистрируйте webhook:

```bash
export APP_URL=https://your-public-url.example
python scripts/set_webhook.py
```

Если Telegram ID ещё неизвестен, сначала задайте токен и webhook-secret, зарегистрируйте webhook и отправьте боту `/whoami`. После этого добавьте полученный ID в `ALLOWED_TELEGRAM_USER_IDS` и настройте `DATABASE_URL`.

## Отчёт по партнёрам

Команда `/report_agents` формирует Excel по всем партнёрам, созданным с 01.10.2025, кроме группы ГТО (`group_id = 2`). Проект относится к партнёру по `projects.partner_id` и считается оплаченным только при зелёном флаге `projects.is_paid = true`; оплаченная сумма берётся из `projects.paid_amount`. Агентские выплаты берутся из `partner_fee.amount` только при совпадении партнёра у выплаты и проекта и только для оплаченных проектов. В книге есть сводка, полный список партнёров, оплаченные проекты, отдельные выплаты и контроль исключений.

В `/report_agents` (алиас `/reports_agents`) список сущностей **«партнёр-агент» из `partners`** объединяется по двум альтернативным условиям: ответственный за карточку (`partners.manager_id`) имеет роль `partnerManager` **ИЛИ** партнёр прикреплён хотя бы к одному проекту, у которого СКС (`projects.manager_sks_id`) имеет эту роль. Пользователи с ролью `agent` не являются базой подсчёта. Каждый ID партнёра выводится один раз, включая закреплённых за менеджером партнёров без проектов. Дата создания с 01.10.2025 и исключение ГТО сохранены.

Колонка «Основание включения» показывает первое, второе или оба условия. «Ответственные СКС» содержит только СКС подходящих проектов (в том числе неоплаченных), а не владельца карточки; при отсутствии таких проектов — «—». Расчёт показателей не изменён: количество, оплаты и агентские выплаты берутся только по оплаченным проектам с СКС в роли `partnerManager`. Партнёр без таких проектов остаётся с нулями. Обычный менеджер проекта (`projects.manager_id`) не фильтруется. На листе «Оплаченные проекты» указан конкретный СКС. Все листы загружаются в одной согласованной read-only транзакции.

### Отчёт по конкретному агенту

`/report_agent` → даты → ответ с частью имени/названия → кнопка подтверждения → Excel.
Можно сразу отправить `/report_agent 2026-08-01 2026-08-31`. Оба конца периода включены, максимальный интервал — 366 дней.

Период относится **к дате создания проекта**, не к датам платежей. В соответствии с образцом «Отчёт по агентам (оплаты)» включаются проекты с `paid_amount > 0`, в том числе частично оплаченные и без зелёного флага. Это отличается от старого `/report_agents`, который не меняется. Сумма — текущее накопленное значение `projects.paid_amount`, не исторический остаток на конец периода. Агент определяется по текущему `projects.partner_id`. Исключается группа агента ГТО (`group_id = 2`); дата создания агента не ограничена.

Сводка: количество проектов с оплатой, сумма, средний чек (сумма / количество проектов), доля в оплаченной сумме всех агентов без ГТО с тем же периодом создания проектов. Детализация сохраняет восемь колонок образца, добавляет ID проекта, номер договора и зелёный флаг для сверки. Средний чек, количество, сумма и доля в Excel связаны формулами с детализацией и отдельной базой доли. Один проект = одна строка; компания с несколькими проектами учитывается несколько раз. Доступ — только пользователям общего разрешённого списка в личном чате.

## Отчёт СКС

Команда `/reports_sks` показывает быстрые периоды и календарь для произвольных дат. Сначала бот отправляет общую PNG-инфографику с KPI, сравнением специалистов, согласованными отчётами, задачами и аномалиями, затем подробный Excel. В книге остаются сводка, контроль СОУТ/других услуг, разрез по услугам и специалистам, задачи, проектная детализация и отдельная вкладка аномалий.

Правила расчёта:

- согласование СОУТ — от входа в этап `Согласовать отчет у клиента` до перехода в `Актуализировать РМ / Прикрепить декларацию`;
- согласование других услуг — до перехода в `Распечатка`;
- отправка СОУТ — от `Отправить документы клиенту` до `Выгрузить протоколы в ФСА`;
- отправка других услуг — до перехода в `Закрыть проект`;
- как в контрольной Google-таблице, количество согласованных отчётов считается по всем СКС, а сумма — по основным шести специалистам: Иванова Елена, Максимович Анастасия, Хасанова Азалия, Орлова Полина, Сластина Ангелина и Григорьева Алёна;
- среднее время отправки считается по всем проектам СКС как среднее из двух показателей: среднего по СОУТ и среднего по остальным услугам;
- в отдельном блоке отправки считаются все закрытые задачи, назначенные Балакиревой Диане или Кулешевой Владиславе через `task_user`; общий итог считает уникальные задачи;
- время задач считается для выполненных задач, название которых содержит `Договор` или `Счет`, но не содержит `ЭДО`; регистр, `ё/е` и лишние пробелы не влияют; задачи с полной календарной длительностью 14 часов и более полностью исключаются, для оставшихся учитываются будни 08:00–17:30 по Москве;
- закрытые задачи отправки считаются по точному названию `отправка` и исполнителям из `task_user`.
- длительность строго больше 200 дней считается аномальной и исключается из средних, минимума, максимума и сравнения времени с планом; сам проект и его стоимость сохраняются в количестве и суммах.

Планы для сравнения: 4 дня, 30 минут, 43 отчёта и 1 500 000 рублей. Они применяются к выбранному периоду без автоматического пересчёта.

## Отчёт ДОТ

Команда `/reports_dota` показывает быстрые периоды и календарь. Бот отправляет общую PNG-инфографику, четыре крупные тематические картинки и Excel. Отдельные изображения: круговая диаграмма ОПР по отделам, круговая диаграмма обучения по компаниям, ежедневная динамика ОПР и ежедневная динамика обучения. Excel содержит сводку, ежедневную динамику запусков и выпусков, а также две таблицы с проектной детализацией.

Графики обновлены 14.09.2026: единый светлый стиль, доли с процентами и суммами, читаемые колонки значений. Для периодов длиннее 45 дней дневные графики используют линии без агрегации данных; для коротких — парные столбцы. Графики КС подстраивают высоту под число строк. [Аудит всех отчётов и список следующих доработок](docs/report-audit-2026-09-14.md). Бизнес-расчёты при обновлении графики не менялись.

Направления отчёта: ОПР (`opk` и `opk_eth`), аутсорсинг, СУОТ, обучение, аудит и другие услуги. Показатели считаются по дате достижения целевого этапа CRM; предыдущий этап не ограничивается:

- запуск ОПР, аутсорсинга, СУОТ и аудита — `Принять проект`;
- запуск обучения — `Передать заявку в УЦ`;
- запуск других услуг — `Передать специалисту исходные данные`;
- выпуск ОПР и СУОТ — `Согласовать отчет у клиента`;
- выпуск аутсорсинга и аудита — `Подготовить документы`;
- выпуск обучения — `Выдать удостоверение Заказчику`;
- выпуск других услуг — `Передать документы Заказчику`.

Сумма берётся из `projects.sale_price`; для запуска ОПР количество РМ берётся из `projects.workplace_count`, для выпуска — фактическое значение `projects.real_workplace_count`. Повторное достижение одного показателя тем же проектом внутри периода учитывается один раз. Предыдущий период — те же календарные даты прошлого месяца: для 01–18 августа это 01–18 июля.

В детализации вместо специалиста СКС показывается отдел менеджера. ГТО определяется по `group_id = 2`, ОАП — по ролям партнёрского/агентского менеджера, КАМ — по согласованному списку менеджеров, остальные менеджеры относятся к ОП.

Планы задаются помесячно через `DOTA_PLANS_JSON` и не пересчитываются пропорционально выбранным дням. Для периода внутри одного месяца отчёт берёт план этого месяца; если план не добавлен или период пересекает месяцы, в плановых колонках выводится прочерк.

## Аналитика КС

Команда `/reports_ks` открывает общий отчёт и четыре самостоятельных раздела:

- `/reports_ks_all` — единый Excel со сводкой, отделами, продуктами, менеджерами, воронкой, проектами, оплатами и детализацией;
- `/reports_ks_plan` — план-факт по кассе, возникновению, лидам, КП и проектам;
- `/reports_ks_managers` — активность и конверсия менеджеров;
- `/reports_ks_funnel` — фактическая и необходимая воронка;
- `/reports_ks_projects` — проекты по первому назначению, их оплаты и ожидаемые суммы.

После выбора дат бот последовательно предлагает отдел, продукт, вариант сравнения и менеджеров. Можно выбрать всех, одного сотрудника кнопкой или ввести до десяти конкретных менеджеров через запятую. Если выбран конкретный отдел, список кнопок ограничивается его сотрудниками. Результат состоит из PNG-графика для быстрого просмотра в Telegram и Excel-файла с расчётами и детализацией. Общий отчёт объединяет все разделы в одном файле, но использует те же расчёты, что и отдельные команды.

Правила расчёта:

- контур КС — 22 конкретных ID в `reporting_bot/ks_scope.py` по согласованному листу «01.09» файла «Сентябрь 2026.xlsx»: ОП (9), ОП Сибирь (4), КАМ (3), СпецКАМ (1), АОП (5). Включены пять согласованных сотрудников ГТО; остальные пользователи автоматически не добавляются. Распределение используется также для предыдущего периода. Изменения состава требуют обновления этого справочника, CRM не изменяется;
- период формирует когорту по `requests_clone.created_at`; лид — любая поступившая неудалённая и неархивная заявка независимо от её текущего статуса;
- КП — каждая запись `offers` по дате `offers.created_at`, ответственному менеджеру заявки, независимо от даты создания заявки;
- дата возникновения — минимальная `systemlogs.created_at` по изменению `expert_id` ИЛИ `measurer_id` с пустого на непустое. Минимум ищется за всю историю, а не только в выбранном периоде. Повторные назначения не создают новый запуск;
- возникновение — `projects.sale_price` один раз на ID проекта, если первая дата назначения входит в период. Отсутствие/архивация заявки не исключает проект. Дата создания проекта не подставляется при отсутствии записи о назначении;
- касса — сумма положительных неудалённых `payment.amount` по дате `payment.chargeAt`, независимо от создания заявки или назначения эксперта. Частичные и повторные платежи складываются, возвраты исключаются. Без даты оплаты или связи с проектом платёж не включается;
- проекты и касса относятся к `projects.manager_id`, не эксперту и не СКС. Используется текущий ответственный, без восстановления истории переводов;
- оплаты/остатки на листе проектов — все положительные платежи выбранных проектов на момент выгрузки, не только в периоде. Остатки считаются отдельно на проект как `max(sale_price − оплаты, 0)`, затем суммируются;
- конверсия считается когортно: заявки с текущим статусом `Успешно` / все заявки когорты × 100%;
- согласованный проект — проект, который по `projects_steps_history` достиг этапа `Распечатка`, даже если затем перешёл дальше;
- звонки остаются операционной активностью и отбираются по фактической дате звонка;
- план-ориентир — факт предыдущего аналогичного периода до загрузки официальных планов;
- прогноз для незавершённого периода рассчитывается пропорционально рабочим дням.

Листы «Правила расчёта» и «Состав КС» показывают методику и конкретные ID сотрудников. Детализация содержит ID записи/проекта, дату события, дату заявки, сумму всех оплат и остаток проекта. СОУТ и «соут» нормализованы; «Замеры» не предлагаются как отдельный продукт. Все данные отчёта читаются в одной read-only repeatable-read транзакции. При превышении 10 000 записей одного вида бот просит сократить выборку вместо незаметного обрезания.

Проверки SQL на изолированных CTE без записи в CRM: `KS_TEST_DATABASE_URL=... pytest tests/test_ks_scope_postgres.py`.

## Добавление отчёта

Каждая запись в `reports.json` содержит:

- `id` — команда отчёта;
- `title` и `description` — подпись в Telegram;
- `parameters` — разрешённые имена параметров;
- `max_rows` — лимит от 1 до 500;
- `sql` — один `SELECT` или `WITH ... SELECT` без изменяющих операций.

Пример:

```json
{
  "id": "sales_by_period",
  "title": "Продажи за период",
  "description": "Выручка по отделам",
  "parameters": ["date_from", "date_to"],
  "max_rows": 100,
  "sql": "SELECT department, SUM(total_amount) AS revenue FROM orders WHERE created_at >= CAST(:date_from AS DATE) AND created_at < CAST(:date_to AS DATE) + INTERVAL '1 day' GROUP BY department ORDER BY revenue DESC"
}
```

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | случайная строка из букв, цифр, `_`, `-` |
| `APP_URL` | production URL приложения без завершающего `/` |
| `ALLOWED_TELEGRAM_USER_IDS` | Telegram ID через запятую |
| `ALLOWED_TELEGRAM_USER_IDS_EXTRA` | дополнительные Telegram ID без замены основного списка |
| `DATABASE_URL` | URL PostgreSQL для read-only пользователя |
| `REPORTS_PATH` | путь к JSON с отчётами |
| `DB_STATEMENT_TIMEOUT_MS` | максимальное время SQL-запроса |
| `DB_CONNECT_TIMEOUT_SECONDS` | таймаут подключения к БД |
| `DEFAULT_MAX_ROWS` | лимит строк по умолчанию |
| `DOTA_PLANS_JSON` | помесячные планы ДОТ в JSON; после изменения нужен новый deploy |

Пример `DOTA_PLANS_JSON`:

```json
{"2026-09":{"Запуск":{"ОПР":3000000,"Аутсорсинг":3400000,"СУОТ":300000,"Обучение":3600000,"Аудит":0,"Другие услуги":1100000},"Выпуск":{"ОПР":2500000,"Аутсорсинг":3400000,"СУОТ":200000,"Обучение":3200000,"Аудит":0,"Другие услуги":350000}}}
```

## Деплой на Vercel

Vercel распознаёт переменную `app` в `app.py` как ASGI-приложение. Добавьте переменные в Production и выполните production deploy. Build hook автоматически зарегистрирует Telegram webhook только для production-окружения.

Важно: Vercel должен иметь сетевой доступ к PostgreSQL. Если база доступна только внутри корпоративной сети/VPN, разместите сервис в той же сети или настройте безопасный прокси/туннель; не открывайте БД всему интернету.
